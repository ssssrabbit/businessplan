1. 全体像

iOS上でオンデバイス実行する俳句生成モデルを作る試み(Apple純正のApple Intelligence機構は 使用せず、MLX Swiftで独自に実装)。核となる生成ロジックは llmjp/generate_haiku.py(Python/HuggingFace Transformers、プロトタイプ環境)と、 その移植である llmjp/haiku_mlx_smoketest/(Swift/MLX、実機デプロイ先)の2系統で 並行開発している。本記録はPython側プロトタイプでの検証結果を中心に、Swift/MLX側との 互換性確認までをまとめる。

最重要の発見

本番で使われていたモデル(haiku-150m-merged)のLoRAは、85,414件・3epochの 設計に対し実際には50ステップしか学習されていなかった(動作確認用の短時間実行結果を 誤ってmergeしていた)。train_loss=5.27は収束には程遠い値で、これまでの生成品質は LoRAチューニングではなくベースモデル自体のプロンプト追従能力に大きく依存していた。

2. 生成パイプラインの構造

五七五の構造を厳密に満たすため、句を「上句(5音)→中句(7音)→下句(5音)」の順に 逐次ビームサーチで埋める3段階方式を採用している。

入力語セット決定 — 1〜2語の入力に対し、季語かどうかを判定し (季語でなければ季節に応じた季語を抽選)、語の配置パターン(上句/中句/下句のどこに 固定するか、最大6通り)を音数の制約で絞り込む。
↓
第1段階: 上句(5音) — model.generate()を num_samples=16でバッチサンプリングし、文節境界・モーラ数(=5)を満たす候補のみ残す。
↓
第2段階: 中句(7音) — 上句の候補ごとに同様に生成。 上句で使われた名詞・動詞(表層形/読み)および他スロットの固定語との重複を禁止する。
↓
第3段階: 下句(5音) — 同様に生成し、完成した17音の句を得る。
↓
評価・ランキング — 季重なり判定、N-gramベースの新規性スコア (現代俳句DB 27,881句との文字バイグラム類似度)、Apple NaturalLanguageによる感情分析、 入力語含有ボーナスを合算したrank_scoreで上位を選ぶ。

主要ファイル

  • generate_haiku.py3段階ビームサーチ本体、パターン横断バッチ化、CLIエントリポイント
  • haiku_analyzer.pyモーラ解析(Janome)・季語判定・新規性・感情分析
  • train_haiku_model.pyLoRA / フルファインチューニング学習スクリプト
  • prepare_dataset.pygendai_haiku.dbからSFT用JSONLを生成
  • bench_pipeline.py速度・質(strict575率・季重なり率・rank_score)の比較計測
  • haiku_mlx_smoketest/Swift/MLX移植版(推論エンジン・ビームサーチ・季語/新規性/感情のSwift実装)

蒸留(§5)の教師データを作る準備の過程で、既存の学習基盤を調査していたところ、本番モデルの LoRA学習が実質ノーオペレーションだったことが判明した。

学習ステップ数508,010
train_loss5.273.92
eval_loss—3.56

生成句を目視比較すると差は明確だった。

ユーザー承認のうえ、haiku-150m-merged/haiku-150m-finetunedを 再学習版に置き換え、旧版は-v1-undertrainedサフィックスで保存した。 副産物として、非日本語文字(全角括弧・ラテン文字・まれにアラビア文字)が句に混入する 既知の軽微な不具合も発見した(v1/v2どちらにも同程度存在、モーラカウントが仮名のみを 数えるため検出をすり抜ける)。

4. 量子化以外の高速化策の検証

実機(iPhone上のオンデバイス実行)ではMLX/Swift経由でNPU・GPUを使う想定のため、 Python/PyTorch側のCPU速度自体は直接の問題にならないが、量子化以外の最適化が アルゴリズムレベルで有効かを検証した(CPU計測、各ケース3回平均)。

施策ごとの合計所要時間(12ケース合計、num_patterns=2・4)
施策内容所要時間判定
ベースライン逐次呼び出し152.4秒—
A: パターン横断バッチ化複数パターンを1回のバッチ推論にまとめる153.4秒効果なし(誤差範囲)
B: KVキャッシュ再利用指示文プレフィックスのキャッシュを使い回す(未測定)断念 — HF内部APIの数値的非互換性
C: モーラ早期停止max_new_tokensを実測値ベースで15/18→10/13に削減158.3秒効果なし(誤差範囲)、歩留まりは不変
施策Bを断念した理由

HFのpast_key_valuesを手動で組み立ててgenerate()に渡す方式を 試作したところ、1トークン目のlogitsは順位一致するものの値に系統的なズレが生じ、 数トークン後に貪欲デコード結果が分岐した。キャッシュ分割によるRoPE計算順序の違いに 起因すると見られ、根本原因の特定には内部実装への深入りが必要なため、CPU速度が 問題にならないという前提も踏まえて追及を見送った。

CPU環境ではこれらの施策の効果が測定できなかった。原因は候補検証処理 (Janome形態素解析)や外部プロセスの負荷が支配的になりやすいためと推測される。 MLX/Swift側(実機相当)での再検証は未実施。

5. 小型モデルへの蒸留

5.1 当初案: rinna GPT-2系 — MLX非対応で断念

候補として rinna/japanese-gpt2-small(123M)と rinna/japanese-gpt2-xsmall(37M)を検討したが、実機デプロイ先である mlx-swift-lmのモデルレジストリ(LLMModelFactory.swift)を 直接確認したところ、GPT-2アーキテクチャ("gpt2")はサポート対象に 含まれていないことが判明した(Llama, Qwen2, Gemma, Phi, Mistral等は対応)。 Python側でどれだけ良く学習できてもMLXでロードできなければ意味がないため、 このアプローチは断念した。

5.2 方針転換: 教師モデル自体の層枝刈り

確実にMLXで動くことを優先し、教師モデルと同じLlamaアーキテクチャのまま 層数を間引く構造的プルーニングを採用した。

パラメータ内訳(枝刈り前)
部分パラメータ数割合
入力埋め込み(vocab=99,584)51.0M33.5%
出力層 lm_head51.0M33.5%
Transformer本体(12層)50.3M33.0%
合計152.3M100%

多言語語彙(99,584語彙)の埋め込みが全体の67%を占めるため、 層だけを枝刈りしても削減幅は限定的(12→6層で152M→127M、約17%減)。 より大きな削減には語彙枝刈り(実際に使う語彙だけに絞る)が必要だが、 今回はリスクの低い層枝刈りのみを実施した。

枝刈り→回復学習の結果
項目値
層数12 → 6(0,2,4,6,8,10番目を保持)
パラメータ数152.3M → 127.1M (83.5%)

回復学習後 train_loss2.45

MLX実機検証: 成功

枝刈り・回復学習済みモデルをMLX形式に変換し、haiku_mlx_smoketest (Swiftパイプライン)で実際にロード・GPU実行・生成まで確認した。 「蛍烏賊珈琲の火に色うめて」(季語【蛍】[夏]、季重なりなし)を含む5句を11.0秒で生成。 層枝刈りアプローチがMLX/Swiftで実機デプロイ可能であることを実証した。

6. インフラ面の教訓

プロジェクト全体がGoogle Drive配下にあったことに起因する問題を多数経験した。 最終的にプロジェクトをローカルディスク(/Users/takaho/Projects/Haiku)へ 移動して解決した。

ファイルのクラウド専用プレースホルダ化

ディスク空き容量が逼迫すると、モデルファイル(600MB級)や__pycache__の .pycまで実体がクラウドのみになり、アクセス時に再ダウンロードで 数分〜数十分ブロックされる現象が繰り返し発生した。

Google Driveアプリ自体の異常

CPU使用率100%超・メモリ6.9GB・累積CPU時間27時間超という異常状態になり、 ファイルアクセスの有無に関わらずシステム全体の速度を落としていた。

Xcodeビルド成果物の破損

.dSYMバンドル(本来ディレクトリ)がDrive同期で単一ファイル化され、 rsyncでの移動時に見かけ上1TBのファイルとして認識されコピーが停止した。 ビルド成果物(.build等)はそもそも同期・コピー対象から除外すべきだった。

対処: ローカルへの全面移動

作業ディレクトリをGoogle Drive外(/Users/takaho/Projects/Haiku)へ rsyncで移動(ビルド成果物は--exclude)。以降は速度・安定性ともに 問題が解消した。

PyTorch/MPSの長時間ハング

蒸留データ生成をMPS(GPU)で長時間ループ実行すると、メモリリーク (プロセスの物理メモリ使用量が2GB→9.7GBまで増大)や、 -[_MTLCommandBuffer waitUntilCompleted]内でのブロッキング待機からの 回復不能な停止が繰り返し発生した。signal.alarmによるタイムアウトは カーネルレベルのブロッキング待機中は配送されず無力だった。

対処: CPUへの切替

データ生成処理はCPU実行に固定。速度は遅くなるが安定して完走する。 MLX Swift側は別実装(PyTorch MPSバックエンドを使わない)のため、 同種の問題は観測されていない。

7. 再現手順

7.1 教師モデルの正式再学習

cd llmjp
python3 train_haiku_model.py --output_dir haiku-150m-finetuned-v2
python3 merge_lora.py --peft_dir haiku-150m-finetuned-v2 --output_dir haiku-150m-merged-v2
python3 bench_pipeline.py --device cpu --label teacher_v2 --merged_dir haiku-150m-merged-v2

7.2 層枝刈り + 回復学習

python3 prune_model.py --output_dir haiku-127m-pruned --target_n_layers 6

cat dataset/haiku_train.jsonl dataset/distillation_data.jsonl \
  > dataset/pruned_recovery_train.jsonl

python3 train_haiku_model.py \
  --model_id haiku-127m-pruned --full_finetune --device cpu \
  --train_file dataset/pruned_recovery_train.jsonl \
  --eval_file dataset/haiku_eval.jsonl \
  --output_dir haiku-127m-pruned-finetuned

7.3 蒸留データ生成(単語ごとのタイムアウト保護つき)

# まず問題のある入力語を特定(季語のモーラ数>7等)
python3 investigate_slow_words.py --device cpu --timeout 25

# 300件ずつプロセスを再起動しながら目標件数まで生成
./run_distillation_batches.sh 5000 300

7.4 MLX変換とSwift実機検証

python3 -m mlx_lm convert --hf-path haiku-127m-pruned-finetuned \
  --mlx-path haiku-127m-pruned-mlx --dtype float16

# tokenizer_config.json の "tokenizer_class" を
# "TokenizersBackend" → "T5Tokenizer" に書き換える(既知の必須手順)

cd haiku_mlx_smoketest
xcodebuild build -scheme haiku_mlx_smoketest -destination 'platform=OS X' \
  -derivedDataPath .xcodebuild

HAIKU_MLX_MODEL_DIR=.../haiku-127m-pruned-mlx \
HAIKU_SUDACHI_DICT=.../sudachidict_core/resources/system.dic \
HAIKU_GENDAI_DB=.../gendai_haiku.db \
  ./.xcodebuild/Build/Products/Debug/haiku_mlx_smoketest
